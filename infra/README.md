# Christduell — Azure infrastructure (Terraform)

Provisions everything the backend needs to run in Azure:

- **Resource group** — container for all resources
- **Azure Container Registry (ACR)** — stores the backend's Docker images
- **Linux App Service Plan + Web App for Containers** — runs the FastAPI backend,
  pulling images from ACR via a system-assigned managed identity (no stored
  registry credentials)
- **PostgreSQL Flexible Server** — managed Postgres 16 on the cheapest burstable
  tier, with automatic backups and point-in-time restore. Its credentials are
  generated by Terraform and injected into the Web App as `DATABASE_URL`.
- **Notification Hub (namespace + hub + authorization rule)** — push
  notification delivery to iOS/Android; its connection string is injected into
  the Web App as `AZURE_NOTIFICATION_HUB_CONNECTION_STRING`

> **Why managed Postgres, and not SQLite on the file share?** An earlier design
> kept a SQLite file on the App Service's Azure Files mount. That is a single
> writer over SMB: every deploy briefly overlaps two containers holding the same
> file open, which is the corruption case, and the file share has no equivalent
> of point-in-time restore. Postgres costs roughly €18/month more — about five
> subscribers — and removes both problems along with the ban on ever scaling out.

## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/install) >= 1.13
- An Azure subscription and the [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli),
  logged in with `az login` (the `azurerm` provider uses your CLI session by default)

## First-time setup

1. **(Recommended) Create remote state storage** so Terraform state isn't only
   on your laptop:

   ```sh
   az group create -n christduell-tfstate-rg -l westeurope
   az storage account create -n christduelltfstate -g christduell-tfstate-rg -l westeurope --sku Standard_LRS
   az storage container create -n tfstate --account-name christduelltfstate
   ```

   Then uncomment the `backend "azurerm"` block in `providers.tf`.

2. **Copy the variables file and adjust as needed:**

   ```sh
   cp terraform.tfvars.example terraform.tfvars
   ```

   `terraform.tfvars` is gitignored. For the very first `apply` the ACR does not
   exist yet, so point `container_image` at any public image (e.g.
   `nginx:latest`), then update it to the real ACR address once the registry is
   created and the CD pipeline has pushed an image.

3. **Initialize, plan, apply:**

   ```sh
   terraform init
   terraform plan
   terraform apply
   ```

## Wiring up CI/CD

After the first `apply`, fetch the values the GitHub Actions deploy workflow
(`.github/workflows/backend-deploy.yml`) needs as repo secrets:

```sh
terraform output container_registry_login_server
az acr credential show --name <acr-name> --query "{user:username, pass:passwords[0].value}"
az ad sp create-for-rbac --name christduell-deploy --role contributor \
  --scopes "$(terraform output -raw resource_group_name | xargs -I{} az group show -n {} --query id -o tsv)" \
  --sdk-auth
```

Map these to the `ACR_LOGIN_SERVER`, `ACR_USERNAME`, `ACR_PASSWORD`,
`AZURE_CREDENTIALS`, and `AZURE_WEBAPP_NAME` secrets in the repo settings.

## Notes

- The notification hub connection string is marked `sensitive` — use
  `terraform output -raw notification_hub_connection_string` to read it when
  needed, and prefer a secrets manager (e.g. Azure Key Vault) over plain
  `tfvars` for anything beyond local experimentation.
- Default SKUs (`B1` App Service, `Free` Notification Hub namespace) are sized
  for development/testing — bump `app_service_sku` before going to production
  with real users.
- Azure keeps automatic Postgres backups with point-in-time restore
  (`postgres_backup_retention_days`, 14 by default). `scripts/backup-db.sh`
  takes an additional dump you hold yourself — useful before a migration, and
  for the case where the subscription itself is unavailable.
- The database server and its database carry `prevent_destroy`. Renaming them in
  Terraform will fail the plan rather than silently replacing the server and
  taking every account with it.

## Application settings

The Web App is configured entirely through Terraform variables (see
`terraform.tfvars.example`); nothing needs to be clicked in the portal:

- `SECRET_KEY` — generated by Terraform (`random_password.secret_key`) and injected. It lives
  in Terraform state, so keep state remote and access-controlled. Rotating it logs every
  player out. Read it with `terraform output -raw jwt_secret_key`.
- `CORS_ORIGINS` — set `cors_origins` to the web build's origin or the browser will block
  every request from it.
- `BILLING_PROVIDER` — `none` until Stripe is verified and configured. The `fake` provider is
  rejected by a variable validation here *and* by the app at startup, because it would grant
  free subscriptions.
- `PUSH_ENABLED` — leave `false` until an EAS project id and push credentials exist; the
  backend then only logs what it would have sent.

The app applies database migrations on startup (`AUTO_MIGRATE`, default on). That is correct
for one instance — if you ever scale out, turn it off and run `alembic upgrade head` as a
deploy step instead.

### Migrating a database that predates Alembic

A database created by the old `create_all` path has the tables but no `alembic_version`. Stamp
it once, then upgrade:

```sh
alembic stamp 0001 && alembic upgrade head
```

Take a backup first (`scripts/backup-db.sh`).

### Moving existing SQLite data to Postgres

Only relevant if a SQLite deployment ever went live — as of now none did, so a fresh
`terraform apply` creates an empty Postgres and seeds it. If you do need to carry data across,
dump the tables from SQLite and load them in dependency order (player → question → duel →
duelround → duelroundquestion → duelanswer → the research and report tables), then reset the
sequences: `SELECT setval(pg_get_serial_sequence('player', 'id'), max(id)) FROM player;` and so
on for every table with an integer primary key.

## Hardening applied

`https_only`, `always_on` (no cold starts against the SQLite file), a `/health` health check,
TLS 1.2 minimum, and FTPS disabled. The running container image is under `ignore_changes` so
`terraform apply` cannot roll back a deployment made by the CD pipeline.
